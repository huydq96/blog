Kinh nghiệm
Gợi ý hướng trả lời
Khung trả lời: vẽ nhanh state machine → nói rõ điểm "không chắc chắn" → cơ chế reconcile → kết quả.

  • Kết quả: tỷ lệ giao dịch treo, thời gian xử lý khiếu nại, số vụ lệch đối soát/tháng (nếu có số).

Goroutine leak: phát hiện trên production thế nào? Cho ví dụ thực tế.

Kết hợp
Xem đáp án
  • Dấu hiệu: metric go_goroutines (Prometheus) tăng đều không giảm, memory tăng theo.

Timeout khi gọi payment gateway thì transaction DB đang mở xử lý thế nào? Có nên rollback khi ctx cancel mà gateway có thể đã trừ tiền?

Kiến thức
Xem đáp án

Ý chính: câu hỏi là cái bẫy. Không giữ DB transaction mở trong lúc gọi HTTP ra ngoài, vì vừa giữ lock/connection lâu, vừa không có cách "rollback" phía gateway.

  1. Tx1: tạo payment_attempts(status=PENDING, idempotency_key) → commit.
  2. Gọi gateway với ctx timeout riêng.
  3. Tx2: cập nhật kết quả. Nếu timeout thì chuyển UNKNOWN, không đánh FAILED.
  4. Reconcile job / webhook sẽ chốt trạng thái cuối.

Lưu ý: dùng context.WithoutCancel(ctx) (Go 1.21+) cho bước ghi kết quả, để client đóng request không làm mất bản ghi trạng thái.

func (s *Service) Charge(ctx context.Context, b Booking) error {
    att, err := s.repo.CreateAttempt(ctx, b.ID, b.Amount) // commit ngay
    if err != nil { return err }

    cctx, cancel := context.WithTimeout(ctx, 15*time.Second)
    defer cancel()
    res, err := s.gw.Charge(cctx, gateway.ChargeReq{RefID: att.RefID, Amount: b.Amount})

    wctx := context.WithoutCancel(ctx)
    switch {
    case err == nil:
        return s.repo.MarkAttempt(wctx, att.ID, res.Status, res.ProviderTxnID)
    case gateway.IsTimeout(err) || errors.Is(err, context.DeadlineExceeded):
        return s.repo.MarkAttempt(wctx, att.ID, StatusUnknown, "") // reconcile sau
    default:
        return s.repo.MarkAttempt(wctx, att.ID, StatusFailed, "")
    }
}

Phân biệt lỗi retryable và non-retryable khi gọi third-party. Dùng errors.Is/As, sentinel error hay custom type?

Kiến thức
Xem đáp án
  • Retryable: network error, timeout với request idempotent, HTTP 429/502/503/504, mã lỗi "system busy" của đối tác.
  • Non-retryable: 400/401/403/422, sai chữ ký, số dư không đủ, thẻ bị từ chối.
  • Sentinel (var ErrNotFound = errors.New(...)) phù hợp cho so sánh đơn giản. Custom type phù hợp khi cần mang thêm dữ liệu (mã lỗi đối tác, HTTP status). Wrap bằng %w để giữ chain.
type ProviderError struct {
    HTTPStatus int
    Code       string
    Retryable  bool
}
func (e *ProviderError) Error() string { return e.Code }

func isRetryable(err error) bool {
    var pe *ProviderError
    if errors.As(err, &pe) { return pe.Retryable }
    var ne net.Error
    return errors.As(err, &ne) && ne.Timeout()
}

Mutex vs channel vs singleflight: dùng cái nào để chống cache stampede khi nhiều request cùng query tồn phòng một homestay hot?

Kiến thức
Xem đáp án

singleflight (golang.org/x/sync/singleflight): gộp các request cùng key thành 1 lần gọi DB, các request khác chờ và dùng chung kết quả. Mutex toàn cục sẽ serialize mọi key; channel thì phải tự dựng lại cơ chế này.

var g singleflight.Group

func (s *Svc) Availability(ctx context.Context, roomID int64, day string) (*Avail, error) {
    key := fmt.Sprintf("avail:%d:%s", roomID, day)
    if v, ok := s.cache.Get(key); ok { return v.(*Avail), nil }

    v, err, _ := g.Do(key, func() (any, error) {
        a, err := s.repo.LoadAvailability(context.WithoutCancel(ctx), roomID, day)
        if err == nil { s.cache.Set(key, a, 30*time.Second) }
        return a, err
    })
    if err != nil { return nil, err }
    return v.(*Avail), nil
}
Trade-off: singleflight chỉ gộp trong 1 pod. N pod thì vẫn có N query; muốn gộp toàn cụm phải có lock Redis (phức tạp hơn). Kết hợp thêm TTL jitter để key không hết hạn cùng lúc. Cache tồn phòng chỉ dùng cho search/hiển thị; bước đặt phòng luôn kiểm tra lại trên DB.

Graceful shutdown trên Kubernetes: SIGTERM, preStop, drain HTTP server, dừng worker đang xử lý dở.

Kiến thức
Xem đáp án
  1. K8s gửi SIGTERM và đồng thời gỡ pod khỏi Endpoints. Hai việc này không đồng bộ, nên thêm preStop: sleep 5-10s để kube-proxy/ingress kịp ngừng route traffic vào.
  2. App: fail readiness → srv.Shutdown(ctx) (ngừng nhận kết nối mới, chờ request đang chạy) → dừng consumer/worker (commit offset xong mới thoát) → đóng DB.

func main() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
    defer stop()

    srv := &http.Server{Addr: ":8080", Handler: router()}
    var wg sync.WaitGroup
    wg.Add(1)
    go func() { defer wg.Done(); worker.Run(ctx) }() // worker tự thoát khi ctx.Done()

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatal(err)
        }
    }()

    <-ctx.Done()
    health.SetNotReady()
    shCtx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
    defer cancel()
    _ = srv.Shutdown(shCtx)
    wg.Wait()
    db.Close()
}

Viết query kiểm tra phòng trống cho khoảng [start, end).

Kiến thức
Xem đáp án

Hai khoảng [a1,a2) và [b1,b2) giao nhau khi và chỉ khi a1 < b2 AND b1 < a2. Tính cả buffer dọn phòng và booking đang giữ chỗ chưa hết hạn.

-- :start, :end là khoảng khách muốn; :end_buf = :end + buffer của phòng
SELECT 1 FROM bookings
WHERE room_id = :room_id
  AND start_at     < :end_buf
  AND block_end_at > :start
  AND ( status IN (2,3,4)                         -- paid, confirmed, checked_in
        OR (status = 1 AND hold_expires_at > UTC_TIMESTAMP()) )  -- đang giữ chỗ
LIMIT 1;

SELECT 1 FROM room_blocks
WHERE room_id = :room_id AND start_at < :end_buf AND end_at > :start
LIMIT 1;

Điểm cộng: điều kiện hold_expires_at > NOW() giúp việc hết hạn giữ chỗ có hiệu lực ngay lập tức về mặt logic, dù cron dọn dẹp có chạy trễ.

Index nào cho query trên? (room_id, start_at, end_at) hay (room_id, end_at)? Giải thích bằng EXPLAIN.

Kiến thức
Xem đáp án
  • B-tree chỉ dùng được 1 điều kiện range để thu hẹp; cột range thứ 2 chỉ lọc trong index (index condition pushdown).
  • Ở hệ thống booking, phần lớn dữ liệu là booking trong quá khứ. Query luôn hỏi khoảng gần hiện tại, nên end_at > :start loại được gần hết dữ liệu cũ. Vì vậy chọn (room_id, block_end_at, start_at, status): range trên block_end_at, còn start_at/status lọc ngay trong index (covering, không cần đọc row).
  • Nếu chọn (room_id, start_at) thì start_at < :end khớp với toàn bộ lịch sử của phòng, số rows quét tăng dần theo thời gian.

Đọc EXPLAIN: cần thấy type=range, key=idx_room_time, rows nhỏ, Extra: Using where; Using index (covering). Nếu thấy type=ALL hoặc Using filesort thì cần xem lại.

Search "homestay trống ở Cầu Giấy 14h–18h hôm nay, giá < 300k" trên 3000+ phòng: MySQL thuần có chịu được không? Khi nào cần Elasticsearch/Redis?

Kết hợp
Xem đáp án

Isolation level mặc định của InnoDB? Phantom read ảnh hưởng kiểm tra overlap thế nào? Gap lock/next-key lock có cứu được không?

Kiến thức
Xem đáp án
  • Mặc định REPEATABLE READ. SELECT thường đọc snapshot: 2 transaction cùng chạy đều không thấy overlap → cùng INSERT → overbook. Đây là "write skew", không phải lỗi cấu hình.
  • SELECT ... FOR UPDATE trên range dùng next-key lock, về lý thuyết chặn insert vào khoảng đó. Tuy nhiên: phạm vi lock phụ thuộc index được chọn; điều kiện 2 cột range khiến lock rộng hơn cần thiết; khi khoảng trống thì 2 tx đều lấy được gap lock (gap lock không xung đột nhau) → cả hai INSERT → deadlock.
  • Cách ổn định hơn: khoá row cha SELECT id FROM rooms WHERE id=? FOR UPDATE để serialize mọi thao tác ghi trên cùng 1 phòng (xem câu 21).

func withRetry(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) error {
    for i := 0; i < 3; i++ {
        err := inTx(ctx, db, fn)
        var me *mysql.MySQLError
        if errors.As(err, &me) && (me.Number == 1213 || me.Number == 1205) {
            time.Sleep(time.Duration(20*(i+1)) * time.Millisecond)
            continue
        }
        return err
    }
    return ErrTooMuchContention

Pagination cho danh sách đơn của chủ nhà hàng chục nghìn đơn: offset vs keyset/cursor.

Kiến thức
Xem đáp án
-- Offset: MySQL vẫn phải đọc và bỏ qua 20000 rows

-- Keyset: nhảy thẳng vào index (host_id, created_at, id)
SELECT ... FROM bookings
WHERE host_id = ?
  AND (created_at, id) < (?, ?)      -- cursor từ trang trước

func (r *Repo) CreateHold(ctx context.Context, in HoldInput) (*Booking, error) {
    var b *Booking
    err := withRetry(ctx, r.db, func(tx *sql.Tx) error {
        var buffer int
        // 1. Serialize mọi ghi trên cùng phòng
        if err := tx.QueryRowContext(ctx,
            `SELECT buffer_min FROM rooms WHERE id = ? AND status = 1 FOR UPDATE`,
            in.RoomID).Scan(&buffer); err != nil {
            return err
        }
        endBuf := in.End.Add(time.Duration(buffer) * time.Minute)

        // 2. Kiểm tra overlap (đọc sau lock nên thấy dữ liệu mới nhất)
        var x int
        err := tx.QueryRowContext(ctx, `
            SELECT 1 FROM bookings
            WHERE room_id = ? AND start_at < ? AND block_end_at > ?
              AND (status IN (2,3,4) OR (status = 1 AND hold_expires_at > UTC_TIMESTAMP()))
            UNION ALL
            SELECT 1 FROM room_blocks
            WHERE room_id = ? AND start_at < ? AND end_at > ?
            LIMIT 1`,
            in.RoomID, endBuf, in.Start, in.RoomID, endBuf, in.Start).Scan(&x)
        if err == nil { return ErrNotAvailable }
        if !errors.Is(err, sql.ErrNoRows) { return err }

        // 3. Tạo giữ chỗ
        b = &Booking{RoomID: in.RoomID, Start: in.Start, End: in.End, BlockEnd: endBuf,
            Status: StatusPendingPayment, HoldExpiresAt: time.Now().UTC().Add(10 * time.Minute)}
        return r.insertBooking(ctx, tx, b)
    })
    return b, err
}

Lưu ý: SELECT ... FOR UPDATE trên row đã lock thì đọc bản mới nhất (locking read), không đọc snapshot. Còn query overlap là plain SELECT, nhưng vì mọi writer đều phải lấy lock row rooms trước nên không còn write skew. Chính xác hơn nữa, có thể dùng FOR SHARE/FOR UPDATE cho query overlap, hoặc đặt isolation READ COMMITTED cho tx này.

func (s *Svc) OnPaymentSucceeded(ctx context.Context, bookingID int64, pay Payment) error {
    return s.repo.InTx(ctx, func(tx Tx) error {
        b, err := tx.LockBookingAndRoom(ctx, bookingID)
        if err != nil { return err }
        if b.Status == StatusConfirmed { return nil } // idempotent
        if err := tx.RecordPayment(ctx, pay); err != nil { return err }

        if b.Status == StatusPendingPayment || tx.StillAvailable(ctx, b) {
            return tx.Transition(ctx, b, StatusConfirmed)
        }
        if err := tx.Transition(ctx, b, StatusPaidUnfulfillable); err != nil { return err }
        return tx.EnqueueOutbox(ctx, "refund.requested", RefundReq{BookingID: b.ID, Reason: "slot_taken"})
    })
}

var allowed = map[Status][]Status{
    PendingPayment: {Paid, Expired, Cancelled},
    Paid:           {Confirmed, PaidUnfulfillable, Cancelled},
    Confirmed:      {CheckedIn, Cancelled},
    CheckedIn:      {Completed},
    Completed:      {Settled, Disputed},
    Cancelled:      {Refunded},
}

func (r *Repo) Transition(ctx context.Context, tx *sql.Tx, b *Booking, to Status, reason string) error {
    if !slices.Contains(allowed[b.Status], to) {
        return fmt.Errorf("%w: %s -> %s", ErrInvalidTransition, b.Status, to)
    }
    res, err := tx.ExecContext(ctx,
        `UPDATE bookings SET status = ?, updated_at = UTC_TIMESTAMP() WHERE id = ? AND status = ?`,
        to, b.ID, b.Status)
    if err != nil { return err }
    if n, _ := res.RowsAffected(); n == 0 { return ErrConcurrentUpdate }
    _, err = tx.ExecContext(ctx,
        `INSERT INTO booking_events(booking_id, from_status, to_status, reason, created_at)
         VALUES (?,?,?,?,UTC_TIMESTAMP())`, b.ID, b.Status, to, reason)
    b.Status = to
    return err
}

  • Timeout: đơn giữ PENDING_PAYMENT, attempt ở UNKNOWN. Không báo khách "thất bại" ngay, hiển thị "đang xác nhận". Reconcile sẽ chốt.
func verify(params url.Values, secret, got string) bool {
    keys := make([]string, 0, len(params))
    for k := range params {
        if k != "vnp_SecureHash" && k != "vnp_SecureHashType" { keys = append(keys, k) }
    }
    sort.Strings(keys)
    var sb strings.Builder
    for i, k := range keys {
        if i > 0 { sb.WriteByte('&') }
        sb.WriteString(k + "=" + url.QueryEscape(params.Get(k)))
    }
    mac := hmac.New(sha512.New, []byte(secret))
    mac.Write([]byte(sb.String()))
    expected := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(strings.ToLower(got)))
}

Retry với exponential backoff + jitter, circuit breaker, timeout budget. Khi nào KHÔNG được retry?

Kiến thức
Xem đáp án
func Retry(ctx context.Context, max int, base time.Duration, fn func() error) error {
    var err error
    for i := 0; i < max; i++ {
        if err = fn(); err == nil || !isRetryable(err) {
            return err
        }
        d := base << i                                    // 100ms, 200ms, 400ms...
        d = d/2 + time.Duration(rand.Int64N(int64(d/2))) // equal jitter
        select {
        case <-time.After(d):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return err
}
  • Không retry: request không idempotent (tạo giao dịch/chuyển tiền mà đối tác không có idempotency key), lỗi 4xx nghiệp vụ, khi ctx đã hết budget.
  • Timeout budget: tổng thời gian retry phải nhỏ hơn timeout của request gốc. Không retry ở nhiều tầng cùng lúc (retry amplification).
  • Circuit breaker (sony/gobreaker): đối tác lỗi liên tục thì mở mạch, fail fast và fallback (ẩn phương thức thanh toán đó trên app), tránh cạn goroutine/connection.

func TestCreateHold_NoOverbooking(t *testing.T) {
    repo := newTestRepo(t) // MySQL từ testcontainers, migrate sẵn
    roomID := seedRoom(t, repo)

    const n = 20
    var ok atomic.Int32
    var wg sync.WaitGroup
    ready := make(chan struct{})
    for i := 0; i < n; i++ {
        wg.Add(1)
        go func(i int) {
            defer wg.Done()
            <-ready // cho tất cả xuất phát cùng lúc
            _, err := repo.CreateHold(context.Background(), HoldInput{
                RoomID: roomID, GuestID: int64(i),
                Start: start, End: start.Add(2 * time.Hour),

            if err == nil { ok.Add(1) } else if !errors.Is(err, ErrNotAvailable) {
                t.Errorf("unexpected error: %v", err)

        }(i)
    }
    close(ready)
    wg.Wait()
    require.EqualValues(t, 1, ok.Load())

Xem đáp án

Xem đáp án
