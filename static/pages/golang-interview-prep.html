Q01 Goroutine leak — khi nào xảy ra, detect và fix thế nào?
runtime concurrency Khó ▾

Goroutine leak xảy ra khi goroutine bị block vĩnh viễn và không bao giờ thoát — không được GC thu hồi vì Go runtime vẫn coi đây là goroutine "đang chạy". Hậu quả: memory tăng dần, CPU có thể tăng, và theo thời gian dẫn đến OOM.

Nguyên nhân phổ biến

  • Channel không có receiver/sender: goroutine block mãi tại ch <- data hoặc data := <-ch khi đầu kia không bao giờ sẵn sàng.
  • Context không được propagate: goroutine chạy vô thời hạn vì không nhận ctx.Done() signal.
  • HTTP client thiếu timeout: goroutine treo chờ response từ downstream service chậm hoặc chết.
  • Mutex deadlock: goroutine A giữ lock A chờ lock B, goroutine B giữ lock B chờ lock A.
  • WaitGroup sử dụng sai: wg.Add() sau wg.Wait() hoặc wg.Done() không được gọi.

Cách detect

  • runtime.NumGoroutine(): log định kỳ mỗi 30s. Số tăng đều mà không giảm = leak.
  • pprof goroutine endpoint: GET /debug/pprof/goroutine?debug=2 → xem full stack trace mọi goroutine đang chạy. Rất hữu ích khi debug production.
  • goleak trong unit test: goleak.VerifyNone(t) ở cuối test — fail nếu có goroutine chưa cleanup.
// Pattern chuẩn: luôn truyền context, select với ctx.Done()
func worker(ctx context.Context, jobs <-chan Job) {
    for {
        select {
        case <-ctx.Done():
            return // cleanup & exit khi context cancel
        case job, ok := <-jobs:
            if !ok { return } // channel closed, exit
            process(job)
        }
    }
}

// Graceful shutdown pattern
const numWorkers = 5

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    jobs := make(chan Job, 100) // worker() nhận jobs qua đây
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            worker(ctx, jobs)
        }()
    }
    // Khi nhận SIGTERM: cancel() -> workers nhận Done -> wg.Wait()
    wg.Wait()
}
💡 Từ kinh nghiệm thực tế Tại ATAO Cloud, mỗi WebSocket connection (VM console) là 1 goroutine. Pattern: khi client disconnect, WebSocket handler nhận error → cancel context → worker goroutine nhận ctx.Done() → cleanup gRPC stream → goroutine thoát sạch. Kết hợp với WaitGroup để graceful shutdown đảm bảo không drop connection giữa chừng khi deploy.
Q02 Channel buffered vs unbuffered — trade-off và deadlock scenario?
channel concurrency Khó ▾

Unbuffered make(chan T): synchronous rendezvous — sender block cho đến khi receiver sẵn sàng đọc, và ngược lại. Đảm bảo 2 goroutine "gặp nhau" đúng thời điểm.

Buffered make(chan T, N): asynchronous trong giới hạn N. Sender chỉ block khi buffer đầy, receiver chỉ block khi buffer rỗng. Tách throughput giữa producer và consumer.

Khi nào dùng cái nào

LoạiDùng khiVí dụ
UnbufferedSignaling, handshake, cần guarantee đồng bộdone chan struct{}, pipeline stage
BufferedWorker pool, rate limiting, tách producer/consumer speedJob queue, alert pipeline

Deadlock scenarios

  • Goroutine gửi vào unbuffered channel nhưng không ai receive (và ngược lại).
  • Main goroutine push vào full buffered channel mà consumer chưa start.
  • Tất cả goroutine cùng block → Go runtime panic: all goroutines are asleep - deadlock!
  • Circular dependency: A chờ B, B chờ A — cả 2 đều blocked trên channel của nhau.
// Worker pool pattern — buffered channel
jobs    := make(chan Job, 100)     // buffer producer không block ngay
results := make(chan Result, 100)

var wg sync.WaitGroup
for i := 0; i < numWorkers; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for job := range jobs {  // unblock khi channel closed
            results <- process(job)
        }
    }()
}

// Producer: push job vào channel — bước này thiếu thì pool xử lý 0 job
for _, j := range incomingJobs {
    jobs <- j
}
// Close jobs sau khi push xong → workers thoát range loop
close(jobs)
wg.Wait()
close(results) // safe vì workers đã done
💡 Từ kinh nghiệm thực tế Trong Alert Management System: pipeline alert → grouping → notification dùng buffered channel giữa các stage để tránh slow consumer (notification có network I/O) block fast producer (grouping engine chỉ làm in-memory). Buffer size = số alert có thể queue mà không OOM — thường dựa trên max alert/s × acceptable delay seconds.
Q03 Go memory model — happens-before, race condition, cách detect và fix?
memory sync Khó ▾

Go memory model định nghĩa: goroutine A đảm bảo thấy write của goroutine B khi và chỉ khi có happens-before relationship được thiết lập qua synchronization primitives. Không có sync = undefined behavior.

Synchronization tạo happens-before

  • Channel send happens-before tương ứng channel receive (unbuffered: receive complete → send return).
  • sync.Mutex.Unlock() happens-before Lock() tiếp theo trên cùng mutex.
  • sync/atomic: có sequential consistency — safe cho counter, flag.
  • sync.Once: f() happens-before Do() return ở mọi goroutine.
  • Goroutine start/join: go f() happens-after lệnh gọi; wg.Wait() happens-after wg.Done().

Fix strategies (theo thứ tự ưu tiên)

  • Redesign với channel: "Do not communicate by sharing memory; share memory by communicating." Loại bỏ hoàn toàn shared state.
  • sync.RWMutex: read-heavy workload — nhiều reader đồng thời, write hiếm.
  • sync.Mutex: general purpose, đơn giản nhất.
  • sync/atomic: chỉ cho primitive type (int64, bool, pointer) trên hot path cần performance.
// Race condition — DATA RACE!
var counter int
go func() { counter++ }() // read-modify-write không atomic

// Fix 1: sync/atomic (cho counter đơn giản)
var counter int64
go func() { atomic.AddInt64(&counter, 1) }()

// Fix 2: sync.RWMutex (cho struct phức tạp)
type SafeCache struct {
    mu    sync.RWMutex
    store map[string]string
}
func (c *SafeCache) Get(key string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.store[key]
}

// Detect: go test -race ./... (overhead ~5-10x, chạy trong CI)
💡 Lưu ý quan trọng Race detector chỉ phát hiện race thực sự xảy ra khi test chạy — không phải tất cả potential race. Cần kết hợp với code review kỹ phần concurrent code. Trong CI/CD pipeline nên luôn có go test -race để bắt sớm.
Q04 Nil interface gotcha — tại sao typed nil != nil?
interface gotcha Khó ▾

Interface value trong Go gồm 2 phần: (type, value). Interface chỉ == nil khi cả hai đều nil. Đây là một trong những gotcha nổi tiếng nhất phân biệt senior với junior.

type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

// BUG: trả về (*MyError, nil) != nil interface
func getError() error {
    var err *MyError = nil
    return err  // interface = (*MyError, nil) → NOT nil!
}

err := getError()
fmt.Println(err == nil) // false! 🐛

// FIX: return untyped nil trực tiếp
func getErrorFixed() error {
    var err *MyError = nil
    if err == nil {
        return nil  // return (nil, nil) → IS nil ✓
    }
    return err
}

// Rule: function return error → luôn return nil (untyped)
// không return concrete_nil_pointer

Khi nào gặp trong thực tế

  • Function trả về concrete error type thay vì error interface — middleware check err != nil bỏ qua lỗi.
  • Repository layer trả về *CustomError — service layer check == nil và skip xử lý error.
  • Tại 9Pay: payment result wrapper có thể dính bug này nếu không cẩn thận — transaction thực ra lỗi nhưng code upstream không biết.
💡 Golden Rule Hàm nào return error: luôn return nil (untyped), không return concreteNilPointer. Nếu buộc phải dùng concrete type, assign vào biến error trước rồi compare: var e error = myErr; if e == nil {...}.
Q05 Generics trong Go — khi nào dùng, khi nào không?
generics Go 1.18+ Trung bình ▾

Generics (Go 1.18+) cho phép viết code type-safe mà không cần duplicate hoặc hy sinh type safety bằng interface{}/any. Nhưng Go community rất thận trọng — "clear is better than clever".

NÊN dùng generics

  • Generic data structures: Queue[T], Stack[T], Set[T] — thay thế hoàn toàn interface{}.
  • Utility functions: Map[T,U], Filter[T], Contains[T comparable] — viết một lần, dùng mọi type.
  • Type-safe wrappers: Result[T], Option[T] — tránh nil pointer và interface boxing.

KHÔNG nên dùng generics

  • Khi interface đủ dùng — nếu chỉ cần gọi method, interface clean hơn và không có compile overhead.
  • Logic khác nhau theo type — phải dùng type switch, generics không giúp được.
  • Hot path performance-critical — generics có dictionary passing overhead, không inline tốt bằng concrete type.
// Generic utility — hữu ích thực tế
func Contains[T comparable](slice []T, item T) bool {
    for _, v := range slice {
        if v == item { return true }
    }
    return false
}

// Generic Result type — tránh error-prone nil check
type Result[T any] struct {
    Value T
    Err   error
}
func (r Result[T]) IsOK() bool { return r.Err == nil }

// Alert Management: check suppressed alerts
if Contains(suppressedFingerprints, alert.Fingerprint) {
    skip()
}
Q06 Slice internals — copy vs share underlying array?
slice memory Cơ bản ▾

Slice là struct{ptr *T, len int, cap int} — không phải array mà là view vào backing array. Điều này gây ra nhiều bug tinh vi khi pass slice qua function hoặc reslice.

// Share backing array: re-slice
a := []int{1, 2, 3, 4, 5}
b := a[:3]         // share! ptr giống a, len=3, cap=5
b[0] = 99          // a[0] cũng thành 99!

// Append trong cap: vẫn share
c := append(b, 10) // len=4, cap=5 → dùng chung array
c[3] = 10          // a[3] = 10! surprise bug

// Append vượt cap: allocate mới, tách biệt
d := append(c, 1, 2, 3) // cap 5 → allocate mới, safe

// Safe: explicit copy
safe := make([]int, len(a[:3]))
copy(safe, a[:3]) // độc lập hoàn toàn

// BUG phổ biến: append trong function không affect caller
func addItem(s []int, v int) {
    s = append(s, v) // slice header được copy vào function
    // nếu append tạo mới backing array → caller không thấy!
}
// Fix: return slice hoặc pass *[]int
💡 Rule of thumb Khi pass slice vào function và muốn mutation safe: dùng copy() trước, hoặc return slice mới thay vì mutate in-place. Với large slice cần avoid copy: pass *[]T hoặc dùng shared mutable struct với mutex.
Q07 Context package — semantic, rules, và khi nào nên dùng gì?
context cancellation Trung bình ▾

Context package giải quyết vấn đề Go không có keyword nào để kill goroutine. Nó cho phép propagate cancellation, deadline, timeout và request-scoped values qua call chain.

Interface của Context

type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done()     <-chan struct{}   // closed khi context bị cancel
    Err()      error             // nil nếu chưa cancel
    Value(key any) any           // request-scoped data
}

4 constructor functions & khi nào dùng

  • WithCancel(parent): tạo context có thể cancel thủ công. Dùng khi muốn cancel từ bên ngoài (user abort, shutdown signal).
  • WithTimeout(parent, d): tự cancel sau duration d. Dùng cho HTTP call, DB query có time budget. Phổ biến nhất.
  • WithDeadline(parent, t): tự cancel tại absolute time t. Dùng khi có SLA cụ thể ("xử lý xong trước 23:59").
  • WithValue(parent, k, v): đính kèm request-scoped data (trace ID, user ID). Không dùng để truyền function params.

Rules quan trọng (phải nhớ)

  • Tạo context sớm nhất có thể — ngay khi nhận request. Từ Go 1.7, http.Request đã chứa context.
  • Không lưu context trong struct — truyền tường minh làm param đầu tiên của function.
  • Mọi function thực hiện I/O (DB, HTTP, gRPC) đều phải nhận và tôn trọng context.
  • Luôn defer cancel() ngay sau lệnh With — không cancel = goroutine/resource leak.
  • Khi parent cancel → tất cả child context cũng bị cancel tự động (tree propagation).
  • Không truyền nil context — dùng context.Background() hoặc context.TODO().
// Pattern chuẩn: HTTP handler → service → repository
func (h *Handler) GetUser(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
    defer cancel() // LUÔN defer cancel

    user, err := h.svc.GetUser(ctx, userID)
    // context propagate xuống service → repo → DB query
    // nếu client disconnect: r.Context() cancelled → ctx cancelled
    // → DB query bị abort → không waste resource
}
💡 Context Value key type Không dùng string làm key cho WithValue — collision risk giữa packages. Dùng unexported custom type: type contextKey int; const requestIDKey contextKey = 0. Đây là idiomatic Go để avoid collision và type-safe context lookup.

Rune vs Byte

  • byte = uint8: 1 byte, đại diện ASCII hoặc raw binary data.
  • rune = int32: 4 bytes, đại diện 1 Unicode code point. Dùng khi làm việc với UTF-8 string có ký tự đặc biệt (tiếng Việt, emoji, CJK).
// Sai: range string theo byte index
s := "hello, 世界"
fmt.Println(len(s))        // 13 bytes, không phải 9 ký tự!

// Đúng: range string cho rune
for i, r := range s {
    fmt.Printf("%d -> %c\n", i, r)
    // 7 -> 世 (index 7, chiếm 3 bytes UTF-8)
}

// Đúng: convert sang []rune để thao tác ký tự
runes := []rune(s)
fmt.Println(len(runes))    // 9 ký tự

// Map: nil map READ ok, WRITE panic
var m map[string]int
_ = m["key"]      // ok, returns zero value
m["key"] = 1    // PANIC: assignment to nil map
m = make(map[string]int)
m["key"] = 1    // ok

type Writer interface {
    Write(p []byte) (n int, err error)
}
// os.File, bytes.Buffer, net.Conn — không cần "implements Writer"

// Type assertion & type switch
func Print(v any) {
    switch t := v.(type) {
    case string:  fmt.Println("string:", t)
    case int:     fmt.Println("int:", t)

    }
}

Ưu và nhược điểm

  • Ưu: Loose coupling, dễ mock test, retrofit existing type kể cả từ external package, compose interface nhỏ.
  • Nhược: Không biết type implement interface nào chỉ bằng nhìn vào struct — cần tooling (gopls, IDE). Typed nil gotcha (Q04).
Q10 Go Scheduler — mô hình M:N, GMP, GOMAXPROCS hoạt động thế nào?
scheduler GMP goroutine Trung bình ▾

Go runtime dùng mô hình M:N scheduler: multiplexes M goroutines onto N OS threads, cho phép hàng nghìn goroutine chạy trên vài OS thread.

GMP Model

  • G (Goroutine): unit of work, lightweight (~2-8KB stack ban đầu, grow dynamically). Không phải OS thread.
  • M (Machine): OS thread thực sự. M chạy goroutine khi được gắn với P.
  • P (Processor): logical processor, số lượng = GOMAXPROCS. P giữ local run queue của goroutines. M phải có P để chạy Go code.

Scheduling hoạt động

  • Mỗi P có local run queue. Khi queue empty → work stealing từ P khác → maximize CPU utilization.
  • Goroutine block on syscall: M tách khỏi P, P attach sang M khác → không block các goroutine khác.
  • Network I/O: goroutine park, netpoller (epoll/kqueue) wakeup khi data ready.
  • Preemptive scheduling từ Go 1.14: signal-based, không cần goroutine yield explicitly.
// GOMAXPROCS mặc định = số logical CPU (Go 1.5+)
fmt.Println(runtime.GOMAXPROCS(0)) // đọc current value

// Goroutine stack: 2-8KB ban đầu, grow đến 1GB default
// OS thread stack: 1-8MB fixed
// → 100,000 goroutines ≈ 200-800MB vs 100,000 threads ≈ không feasible

Q11 Design Alert Management System — grouping, delay, suspend, scale?
kafka redis state machine Khó ▾

Đây là project bạn đã build tại Giaohangtietkiem — trả lời được end-to-end architecture bằng kinh nghiệm thực tế là điểm cộng lớn.

Architecture overview

  • Ingest Layer: Alertmanager webhook → Kafka topic alerts.raw. Mỗi alert có fingerprint = hash(labels). Idempotency: upsert theo fingerprint + time window.
  • Grouping Engine: Consumer đọc từ Kafka, group alerts bằng sliding window (5 phút). Các alert cùng alertname + cluster + severity được gom. Group state lưu Redis với TTL = 1 giờ.
  • State Machine: firing → acknowledged → resolved → closed. Mỗi transition log vào MySQL với timestamp + actor để audit.
  • Delay/Suspend Queue: Redis Sorted Set, score = unix timestamp execute_at. Worker poll mỗi 5s: ZRANGEBYSCORE 0 now → process → ZREM.
  • Notification Worker: Consume alerts.notify, fan-out sang email/Slack/PagerDuty.

Scale strategy

  • Partition Kafka theo alert_source/cluster → mỗi partition xử lý độc lập.
  • Horizontal scale consumer group → thêm instance tự nhận partition.
  • Redis Cluster cho group state → sharding theo group key hash.
  • MySQL chỉ lưu metadata + state transitions, không lưu raw alert payload → size manageable.

Handle flapping alerts (alert bật/tắt liên tục)

  • Re-resolve threshold: alert phải ở state "resolved" > X phút mới thực sự close — tránh close sớm rồi reopen.
  • Inhibition rule: nếu parent alert firing, suppress child alerts.
  • Repeat interval: không re-notify nếu alert chưa đổi state sau lần notify trước.
// Delay queue với Redis Sorted Set (rdb là *redis.Client, go-redis v9)
// Delay alert X đến thời điểm T
rdb.ZAdd(ctx, "delay_queue", redis.Z{
    Score:  float64(executeAt.Unix()),
    Member: alertID,
})

// Worker poll mỗi 5 giây
func pollDelayQueue(ctx context.Context) {
    ticker := time.NewTicker(5 * time.Second)
    for {
        select {
        case <-ctx.Done(): return
        case <-ticker.C:
            now := fmt.Sprintf("%d", time.Now().Unix())
            ids, _ := rdb.ZRangeByScore(ctx, "delay_queue", &redis.ZRangeBy{
                Min: "0", Max: now,
            }).Result()
            for _, id := range ids {
                processAlert(id)
                rdb.ZRem(ctx, "delay_queue", id)
            }
        }
    }
}
💡 Exactly-once processing Interviewer hay hỏi: đảm bảo exactly-once thế nào? Trả lời: at-least-once (Kafka) + idempotent handler (upsert theo fingerprint + idempotency key) = effectively exactly-once. True exactly-once (Kafka Transactions) có overhead quá cao và thường không cần thiết khi handler idempotent.

Outbox Pattern (khuyến nghị cho Fintech)

// 1 DB transaction: write payment + outbox event (atomic)
tx.Exec("INSERT INTO payments VALUES (...)")
tx.Exec("INSERT INTO outbox (event_type, payload, published) VALUES (?, ?, false)",
    "payment.created", payload)
tx.Commit() // atomic: cả 2 hoặc không cái nào

// Relay worker: poll outbox → publish Kafka → mark published
rows, err := db.Query("SELECT id, event_type, payload FROM outbox WHERE published=false ORDER BY id LIMIT 100")
if err != nil { return err }
defer rows.Close()

for rows.Next() {
    var id int64
    var eventType, payload string
    if err := rows.Scan(&id, &eventType, &payload); err != nil {
        return err // dừng batch này, lần poll sau sẽ retry từ đầu
    }
    kafka.Publish(eventType, payload)
    db.Exec("UPDATE outbox SET published=true WHERE id=?", id)
}
// Nếu app crash sau DB commit nhưng trước Kafka publish
// → relay service vẫn pick up khi restart

  • Client gửi X-Idempotency-Key: uuid trong header mọi request chuyển tiền.
  • Server store key + result vào Redis với TTL = 24h.
  • Duplicate request (bank retry sau timeout) → trả về cached result, không process lại.

Dùng circuit breaker (sony/gobreaker): error rate > threshold → open circuit → fail fast với ErrCircuitOpen, không hammer bank API đang lỗi. States: Closed → Open → Half-Open → Closed. Distributed rate limiting — Redis + Lua script

-- Lua: atomic token bucket check (không bị race condition)
local key      = KEYS[1]
local capacity = tonumber(ARGV[1])
local now      = tonumber(ARGV[2])
local rate     = tonumber(ARGV[3])  -- tokens/second

local last   = tonumber(redis.call("HGET", key, "last")) or now
local tokens = tonumber(redis.call("HGET", key, "tokens")) or capacity

-- Refill tokens based on elapsed time
tokens = math.min(capacity, tokens + rate * (now - last))

if tokens >= 1 then
    tokens = tokens - 1
    redis.call("HMSET", key, "last", now, "tokens", tokens)
    redis.call("EXPIRE", key, 3600)
    return 1  -- allowed
end
return 0  -- rejected

Q15 Kafka consumer lag, rebalancing — debug và tối ưu thế nào?
kafka consumer group Khó ▾

Consumer lag = latest offset - committed offset. Lag tăng = consumer xử lý chậm hơn producer produce. Nếu không fix → OOM khi backlog quá lớn.

Root cause của lag

  • Processing quá chậm: downstream DB slow query, external API timeout, heavy computation.
  • Consumer crash/restart liên tục: mỗi rebalance cần warm-up time.
  • Partition count quá ít: 1 partition max 1 consumer/group → không scale được.
  • Message size quá lớn: network bandwidth bottleneck.

Troubleshooting checklist

  • kafka-consumer-groups.sh --describe: xem lag per partition, identify partition bị lag nhất.
  • Verify consumer count == partition count (nếu không → một số instance idle, lãng phí).
  • Trace processing time per message từ receive → ack để tìm bottleneck.
  • Check downstream: DB slow query log, Redis latency, external API p99.

Fix strategies

  • Scale horizontally: tăng partition count → tăng consumer instance (phải theo thứ tự: partition trước).
  • Batch processing: bulk insert N messages thay vì từng message → giảm DB round trips.
  • Parallel processing trong consumer: mỗi message spawn goroutine, control với semaphore (bounded concurrency).

Rebalancing — minimize impact

  • Static membership: group.instance.id fixed per pod → restart không trigger rebalance ngay.
  • Incremental cooperative rebalancing (Kafka 2.4+): chỉ reassign partition cần thiết, không stop-the-world toàn bộ group.
  • max.poll.interval.ms phải lớn hơn processing time của batch lớn nhất — nếu không Kafka coi consumer là dead và rebalance.
💡 Từ Alert Management thực tế Alert processing có thể chậm nếu grouping engine query Redis nhiều. Fix: commit offset trước, xử lý async bằng goroutine pool. Trade-off: at-least-once delivery — message có thể process lại nếu crash sau commit. Handler phải idempotent.

func getWithLock(ctx context.Context, key string, ttl time.Duration) (string, error) {
    val, err := rdb.Get(ctx, key).Result()
    if err == nil { return val, nil }  // cache hit

    time.Sleep(50 * time.Millisecond)
    return rdb.Get(ctx, key).Result()
}

Q21 ACID properties và Isolation Levels — dirty read, phantom read là gì?
ACID isolation transaction Khó ▾

ACID Properties

  • Atomicity: Transaction là atomic — toàn bộ thành công hoặc toàn bộ rollback. Không có partial commit.
  • Consistency: Transaction đưa DB từ valid state này sang valid state khác. Integrity constraints luôn được giữ.
  • Isolation: Concurrent transactions không ảnh hưởng nhau — mỗi transaction thấy consistent view của data.
  • Durability: Committed transactions tồn tại vĩnh viễn — kể cả khi system crash sau commit.

4 Isolation Levels (tăng dần độ chặt)

LevelDirty ReadNon-RepeatablePhantom ReadPerformance
READ UNCOMMITTED✅ Có✅ Có✅ CóCao nhất
READ COMMITTED❌ Không✅ Có✅ CóCao
REPEATABLE READ (MySQL default)❌ Không❌ Không✅ Có*Trung bình
SERIALIZABLE❌ Không❌ Không❌ KhôngThấp nhất

* InnoDB dùng MVCC + gap lock để ngăn phantom read trong REPEATABLE READ — khác với SQL standard.

Anomalies giải thích

  • Dirty Read: T2 đọc data T1 chưa commit → T1 rollback → T2 đã dùng data không tồn tại.
  • Non-Repeatable Read: T2 đọc cùng row 2 lần → giữa 2 lần đọc T1 UPDATE và commit → kết quả khác nhau.
  • Phantom Read: T2 query với WHERE điều kiện 2 lần → T1 INSERT row mới thỏa điều kiện giữa 2 lần → số lượng rows khác.

MySQL Deadlocks

Deadlock = T1 chờ lock T2 đang giữ, T2 chờ lock T1 đang giữ → circular wait. MySQL detect tự động và rollback transaction nhỏ hơn (ít undo log hơn). Fix: consistent lock order, short transactions, index để avoid full table lock.

💡 Tại 9Pay Fintech cần REPEATABLE READ (default MySQL) cho payment transaction — đảm bảo balance đọc consistent trong suốt transaction. SERIALIZABLE quá chậm. READ COMMITTED không đủ — có thể thấy intermediate state từ concurrent transaction.
Q22 Composite index vs Single index — left-prefix rule, khi nào chọn cái nào?
composite index left-prefix index merge Khó ▾

Cả hai đều là B-Tree. Composite index (col_a, col_b) = mảng đã sort theo col_a trước, col_b sau. Single index = 2 B-Tree độc lập.

Left-Prefix Rule — Critical

  • INDEX(a,b,c): query WHERE a=1 AND b=2 ✅, WHERE a=1 ✅, WHERE b=2 ❌ (không dùng được).
  • Gap problem: WHERE a=1 AND c=3 → chỉ dùng được cột a, c bị skip vì b không có trong WHERE.
  • Range stop rule: WHERE a=1 AND b>2 AND c=3 → dùng được a và b, nhưng dừng tại range b>2, c không được index-filtered.

Thứ tự cột trong composite index

  • Rule: Equality columns → GROUP BY/ORDER BY columns → Range columns.
  • Đặt cột có cardinality cao (nhiều distinct values) lên đầu để loại bỏ nhiều rows sớm nhất.
  • Nếu đã có INDEX(a, b), tạo thêm INDEX(a) là redundant — vì index (a,b) đã cover query WHERE a=?.

Index Merge — khi không có composite index hoàn hảo

  • Intersection: WHERE col_a=? AND col_b=? → scan idx_a + scan idx_b → intersect row IDs. Hiệu quả hơn full table scan nhưng kém composite index.
  • Union: WHERE col_a=? OR col_b=? → union 2 index results.
  • Xuất hiện trong EXPLAIN Extra: Using intersect(...) / Using union(...).
  • Nếu thấy index merge thường xuyên → nên tạo composite index thay vì để optimizer làm thủ công.
-- Bảng transactions: query phổ biến
SELECT * FROM transactions
WHERE merchant_id = 123
  AND status = 'completed'
  AND created_at > '2025-01-01'
ORDER BY created_at DESC
LIMIT 20;

-- Composite index tối ưu:
-- merchant_id (equality), status (equality), created_at (range+order)
CREATE INDEX idx_merchant_status_date
    ON transactions(merchant_id, status, created_at DESC);

-- EXPLAIN: type=range, key=idx_merchant_status_date
-- Extra=Using index (covering nếu SELECT cột nằm trong index)

Q24 Kafka architecture — Topic, Partition, Consumer Group hoạt động thế nào?
kafka architecture partition Khó ▾

Core components

  • Message/Record: đơn vị data — byte array với optional key. Key dùng để route vào partition cụ thể (same key → same partition → ordering guarantee).
  • Topic: logical category, giống table trong DB. Immutable append-only log.
  • Partition: physical unit, append-only log. 1 topic nhiều partitions. Ordering chỉ đảm bảo trong 1 partition, không phải cross-partition.
  • Offset: vị trí của message trong partition — monotonically increasing integer. Consumer track offset để biết đọc đến đâu.
  • Broker: Kafka server. 1 partition leader + N replicas trên các broker khác.

Consumer Group

  • Multiple consumers cùng group.id chia sẻ partitions — mỗi partition chỉ được đọc bởi 1 consumer trong group tại một thời điểm.
  • Consumer count > partition count → một số consumer idle. Consumer count = partition count → optimal parallelism.
  • Multiple groups → mỗi group nhận full copy của data (fan-out).

Replication và Durability

  • Leader partition nhận ghi từ producer. Follower replicate từ leader.
  • ISR (In-Sync Replicas): tập followers đã nhận và commit tất cả messages từ leader. Leader fail → ISR member được bầu làm leader mới.
  • replication.factor=3 + min.insync.replicas=2 + acks=all → data safe kể cả 1 broker fail.
// Producer config cho Fintech (high durability)
acks = all              // wait all ISR replicas acknowledge
min.insync.replicas = 2 // at least 2 replicas must confirm
enable.idempotence = true // exactly-once producer semantics
retries = 2147483647   // retry forever (với idempotence safe)

// Consumer config: delivery guarantee
enable.auto.commit = false  // manual commit after processing
auto.offset.reset = earliest // nếu no offset: đọc từ đầu
max.poll.interval.ms = 300000 // phải lớn hơn max processing time
💡 Topic Compaction Thay vì xóa data cũ theo thời gian, compaction giữ lại message cuối cùng per key. Hữu ích cho changelog/state store — consumer có thể rebuild state mà không cần replay toàn bộ history. Tại ATAO Cloud: VM state topic dùng compaction — chỉ cần last state per VM ID.
Q25 Kafka Delivery Guarantees — at-least-once vs exactly-once thực tế?
delivery guarantee idempotent offset Khó ▾

3 loại Delivery Guarantee

  • At-most-once: commit offset trước khi process. Message có thể bị mất nếu process fail. Không dùng cho critical data.
  • At-least-once: process xong mới commit offset. Message có thể bị xử lý lại nếu commit fail. Handler phải idempotent.
  • Exactly-once (EOS): Kafka Transactions + idempotent producer. Overhead cao — chỉ dùng khi thực sự cần (financial ledger).

Idempotent consumer — thực tế phổ biến nhất

At-least-once + idempotent handler = effectively exactly-once với cost thấp hơn nhiều so với Kafka EOS.

// Idempotent consumer pattern
func processMessage(ctx context.Context, msg kafka.Message) error {
    // Idempotency key = message key + offset (unique per message)
    idempotencyKey := fmt.Sprintf("%s:%d:%d", msg.Topic, msg.Partition, msg.Offset)

    // Check if already processed (Redis SET NX với TTL, rdb là *redis.Client)
    ok, err := rdb.SetNX(ctx, "processed:"+idempotencyKey, "1", 24*time.Hour).Result()
    if err != nil {
        return err
    }
    if !ok {
        return nil // already processed, skip
    }

    // Process (upsert, not insert — handle duplicate gracefully)
    // db.Exec trả (sql.Result, error) — không gán thẳng vào return error được
    _, err = db.Exec("INSERT INTO events ... ON DUPLICATE KEY UPDATE ...")
    return err
}

// Commit offset sau khi process thành công
// Fail trước commit → message sẽ được retry → idempotent handler safe

Quản lý Offset khi Rebalance

  • Rebalance trigger: consumer join/leave group, partition count change, max.poll.interval.ms vượt quá.
  • Trong rebalance: consumer dừng đọc, partition được redistribute. Uncommitted offsets sẽ được re-processed.
  • Minimize rebalance impact: static membership (group.instance.id), incremental cooperative rebalancing (Kafka 2.4+).
💡 auto.offset.reset earliest: đọc từ đầu partition khi không có committed offset (new consumer group). latest: chỉ đọc message mới. Fintech thường dùng earliest để không bỏ sót message khi deploy consumer group mới.
Q26 KRaft mode — Kafka không cần ZooKeeper, hoạt động thế nào?
KRaft ZooKeeper Kafka 4.0 Trung bình ▾

Kafka 4.0 (phát hành tháng 3/2025) chính thức loại bỏ ZooKeeper, chạy hoàn toàn bằng KRaft (Kafka Raft). Đây là thay đổi kiến trúc lớn nhất trong lịch sử Kafka.

Vấn đề với ZooKeeper

  • Operational complexity: phải maintain 2 cluster riêng biệt (ZK + Kafka), 2 set config, 2 set monitoring.
  • Bottleneck: ZK giới hạn số partition ~100K+ per cluster. Với KRaft có thể scale đến hàng triệu partitions.
  • SPOF: ZK không ổn định → cả Kafka cluster bị ảnh hưởng.
  • Latency: ZK round-trip tạo latency cho metadata operations.

KRaft hoạt động thế nào

  • Quorum Controller: một số broker được đề cử làm controller nodes, tạo thành Raft quorum (thường 3 hoặc 5 nodes).
  • Controller nodes dùng Raft consensus protocol để bầu leader và replicate metadata log.
  • Metadata log = event-sourced store — tất cả thay đổi (topic create, partition reassign, broker join/leave) được append vào log, không phải update in-place.
  • Recovery nhanh: controller mới catch up bằng cách replay metadata log + snapshot.
# KRaft mode config (Kafka 4.0)
process.roles=broker,controller   # combined node
node.id=1
controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093

# Không còn zookeeper.connect config
# Bootstrap: kafka-storage.sh format --config server.properties \
#   --cluster-id $(kafka-storage.sh random-uuid)
💡 Migration path Nếu đang chạy Kafka 2.x/3.x với ZooKeeper: có thể migrate sang KRaft mode bằng migration tool trong Kafka 3.5+. Kafka 4.0 remove ZooKeeper hoàn toàn. Production recommendation: test KRaft trên non-critical cluster trước khi migrate main cluster.

Q28 Creational Patterns — Singleton, Factory, Abstract Factory trong Go?
singleton factory creational Trung bình ▾

Singleton — sync.Once

Đảm bảo chỉ 1 instance trong toàn chương trình. Go dùng sync.Once để thread-safe initialization.

var (
    once     sync.Once
    instance *DBPool
)

func GetDB() *DBPool {
    once.Do(func() {
        instance = newDBPool() // chỉ chạy 1 lần dù nhiều goroutine
    })
    return instance
}
// Tại 9Pay: DB connection pool, Redis client — Singleton pattern

Factory Method — trả về interface, hide implementation

type NotificationSender interface {
    Send(to, msg string) error
}

func NewSender(channel string) NotificationSender {
    switch channel {
    case "email":  return &EmailSender{}
    case "sms":    return &SMSSender{}
    case "slack":  return &SlackSender{}
    default:       return &EmailSender{}
    }
}
// Alert Management: factory tạo notification sender theo config

Abstract Factory — family of related objects

Khi cần tạo nhiều loại object liên quan theo "họ" — ví dụ iOS factory tạo IOSSMSSender + IOSEmailSender, Android factory tạo bộ tương ứng. Client chỉ biết factory interface, không biết concrete type.

Trade-off khi dùng

  • Singleton: hạn chế testability (hard to mock). Tránh overuse. Chỉ dùng cho truly shared resource (DB pool, config).
  • Factory: tăng abstraction nhưng thêm indirection. Hữu ích khi creation logic phức tạp hoặc cần runtime decision.
  • Abstract Factory: phức tạp, nhiều interface. Dùng khi cần swap "họ" implementation theo environment (prod/test/staging).

type CachedMerchantRepo struct {

    cache *redis.Client

func (c *CachedMerchantRepo) FindByID(ctx context.Context, id string) (*Merchant, error) {
    if cached, err := c.cache.Get(ctx, id).Result(); err == nil {

    return m, nil
}

// Observer: Alert notification system
type AlertObserver interface {
    OnAlert(alert Alert)
}

type AlertNotifier struct {
    mu        sync.Mutex
    // map key là interface — an toàn miễn concrete type luôn comparable
    // (không chứa field kiểu slice/map/func)
    observers map[AlertObserver]struct{}
}

func (n *AlertNotifier) Register(o AlertObserver) {
    n.mu.Lock()
    defer n.mu.Unlock()
    n.observers[o] = struct{}{}
}
func (n *AlertNotifier) Deregister(o AlertObserver) {
    n.mu.Lock()
    defer n.mu.Unlock()
    delete(n.observers, o)
}
func (n *AlertNotifier) Notify(a Alert) {
    n.mu.Lock() // Register/Deregister/Notify gọi từ nhiều goroutine → bắt buộc lock
    defer n.mu.Unlock()
    for o := range n.observers { go o.OnAlert(a) } // async notify
}

// Strategy: payment method selection
type PaymentStrategy interface {
    Pay(amount float64) error
}

type PaymentService struct { strategy PaymentStrategy }
func (s *PaymentService) SetStrategy(st PaymentStrategy) { s.strategy = st }
func (s *PaymentService) Execute(amount float64) error {
    return s.strategy.Pay(amount) // runtime swap mà không sửa service
}
💡 Observer vs Kafka Observer Pattern là in-process event notification. Kafka là distributed pub-sub. Khi nào dùng gì:
In-process, same service → Observer (zero latency, no serialization).
Cross-service, async, durable → Kafka (Alert Management: trigger → Kafka → multiple notification consumers).
